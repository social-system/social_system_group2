# 将来検討: レシート正規化と自動補完の安全方針

## 目的

この文書は、OCR レシートの商品名表記揺れ、商品候補提示、数量・単位補完をさらに強化するための将来検討事項を整理する。

ここで扱う機能は、今すぐ実装すると `product_id` や `base_quantity` を誤って確定し、購入履歴・在庫量・価格比較を壊す可能性がある。そのため、現時点では実装しない。

## 基本方針

自動確定してよい条件は、既存方針を維持する。

```text
明示された product_id が存在する
信頼できる active alias の alias_key に完全一致した
products.name_key に完全一致した
```

次の情報は、候補提示や順位付けには使ってよいが、自動 `resolved` や `base_quantity` の確定には使わない。

```text
部分一致
曖昧検索スコア
AI候補
カテゴリ平均
ocr_suggested alias
```

DB に保存してよい確定データは、ユーザー確認または管理者確認を経た値だけである。

## 高度な曖昧検索

### 導入目的

OCR の表記揺れや誤読により、現在の正規化キー完全一致や単純な部分一致では候補に出ない商品を、確認画面で見つけやすくする。

例:

```text
夕マゴ -> タマゴ
牛乳1OOOml -> 牛乳1000ml
ミソ汁用みそ -> 味噌
```

### 期待効果

- 未解決商品の `product_candidates` が増え、ユーザーの検索・選択負荷が下がる。
- alias 登録の機会が増え、次回以降の完全一致解決につながる。
- よく出る未解決 `raw_name` に対して、運用上の改善候補を見つけやすくなる。

### 誤解決リスク

曖昧検索は、文字列が似ているだけで意味が異なる商品を近い候補として出す可能性がある。

例:

```text
豆腐 と 納豆
牛乳 と 乳飲料
米 と 米粉
豚肉 と 鶏肉
```

これを自動確定に使うと、在庫対象の商品 ID が誤って保存される。価格比較や在庫反映では `product_id` が基準になるため、一度誤保存すると後続の集計も壊れる。

### 安全方針

高度な曖昧検索は、`product_candidates` の候補生成または順位付けに限定する。

曖昧検索スコアが高くても、自動で `resolution_status = resolved` にしない。自動 resolved に使えるのは、従来通り信頼できる active alias の完全一致、または `products.name_key` 完全一致だけである。

曖昧検索により候補へ出た商品をユーザーが選択した場合だけ、`POST /product-aliases` により `user_confirmed` alias として学習する。

### 導入前に必要な評価データ

導入前に、少なくとも次の評価データを用意する。

- 実レシートまたは実運用に近い OCR 由来の `raw_name`
- 期待する `expected_product_name`
- 自動解決してよいケースと、候補提示に留めるケースの分類
- 商品カテゴリ別の誤候補例
- 曖昧検索導入前後の未解決率、誤候補率、alias 登録率

評価では、候補に正解が含まれる率だけでなく、誤って最上位になりやすい候補も確認する。

## AI による候補提示

### 導入目的

AI を使って、OCR の `raw_name` や周辺情報から商品候補を並べ替えたり、ユーザー確認画面で見つけやすい候補を提示したりする。

### 安全策

AI 候補は `product_candidates` の順位付け補助に限定する。AI の出力だけで `product_id` を確定しない。

AI が提案した候補から alias を作る場合、その source は `ocr_suggested` とする。`ocr_suggested` alias は候補検索には使ってよいが、自動解決には使わない。

自動解決に使える alias へ昇格できるのは、次の場合だけである。

| 昇格後 source | 条件 |
| --- | --- |
| `user_confirmed` | ユーザーが確認画面で商品を選択した |
| `admin` | 管理者が候補と商品マスタの対応を確認した |

### AI 候補を自動確定に使わない理由

AI は入力の文脈が不足していても、それらしい商品名を返すことがある。レシートの商品名は短く、略称や店舗独自表記も多いため、AI が高信頼に見える候補を返しても正しいとは限らない。

誤った `product_id` を保存すると、購入履歴、在庫反映、最安店比較、将来のレシピ提案がすべて誤った商品を基準に動く。したがって、AI 候補は確認画面の補助情報であり、確定データではない。

### 導入前に必要な条件

- AI 候補の表示位置と根拠を確認画面で区別できること
- `ocr_suggested` alias が自動解決に使われないことをテストで固定すること
- ユーザー確認または管理者確認による source 昇格フローが明確であること
- AI の誤候補率を運用指標で確認できること

## 商品カテゴリごとの数量推定

### 検討内容

商品カテゴリごとに、購入単位から `base_quantity` の初期値を推定する案がある。

例:

```text
野菜 1袋 -> 200g
肉 1パック -> 300g
魚 1切 -> 100g
```

### リスク

野菜、肉、魚などは、同じカテゴリ・同じ単位でも実際の量差が大きい。

```text
トマト 2個 -> ?g
じゃがいも 2個 -> ?g
豚肉 1パック -> ?g
刺身 1パック -> ?g
```

カテゴリ平均で `base_quantity` を確定すると、在庫量が実態から大きくずれる可能性がある。在庫反映では `base_quantity` がそのまま在庫増加量になるため、推定値を保存すると後から補正しにくい。

### 安全方針

カテゴリごとの数量推定を使う場合も、候補提示または初期値入力補助に限定する。

推定値は `POST /receipts/prepare` の確認材料として返してよいが、ユーザー確認なしで `base_quantity` に保存しない。確定保存は、ユーザーが確認画面で修正または承認した後の `POST /receipts` だけで行う。

商品別の安全な変換がある場合は、カテゴリ平均ではなく `product_unit_conversions` を使う。

例:

```text
卵 1パック -> 10個
牛乳 1本 -> 1000ml
米 1kg -> 1000g
```

### 導入前に必要な条件

- 推定値と確定値を API 契約上で区別できること
- 推定値を保存しないことをテストで固定すること
- ユーザーが推定値を確認・修正できる確認画面があること
- 商品別変換テーブルで対応できるものと、カテゴリ推定に留めるものを分類すること

## 家庭ごとの商品マスタ・alias 分離

### 検討内容

家庭ごとに、よく買う商品名、略称、容量、在庫単位が異なる。

例:

```text
A家庭: 牛乳 = 1000ml
B家庭: 牛乳 = 500ml
A家庭: いつもの豆腐 = 300g
B家庭: いつもの豆腐 = 150g
```

そのため、将来的には共通マスタと家庭別データを分ける案がある。

### 案

共通マスタと家庭別 alias を分ける。

```text
products                 共通の商品マスタ
product_aliases          共通または seed/admin alias
household_product_aliases 家庭ごとの略称・OCR表記
```

家庭別 `product_unit_conversions` を持つ。

```text
product_unit_conversions            共通変換
household_product_unit_conversions  家庭ごとの容量差を持つ変換
```

必要であれば、家庭ごとの既定在庫対象や既定カテゴリも分離する。

### リスク

家庭別分離には、認証、世帯管理、ユーザーと世帯の関連付け、データアクセス制御が必要になる。これらがない状態で家庭別データを導入すると、別家庭の alias や変換ルールが混ざり、商品解決や在庫数量を壊す。

また、共通マスタと家庭別マスタの責務が曖昧だと、同じ商品を重複作成したり、alias の衝突処理が複雑になったりする。

### 現時点の判断

家庭ごとの商品マスタ・alias 分離は現時点では非ゴールとする。

理由は、現在のシステムが認証・世帯管理を持たず、単一ユーザー前提で動いているためである。家庭別分離は、認証・世帯管理・アクセス制御を設計してから導入する。

## 今すぐ実装しない理由

この文書の検討事項は、いずれも確認画面の利便性を上げる可能性がある一方で、誤って自動確定すると在庫データを壊す。

特に危険なのは次の状態である。

```text
曖昧検索やAI候補だけで product_id を確定する
カテゴリ平均だけで base_quantity を保存する
家庭ごとの差を無視して alias や変換ルールを共有する
```

これらは、ユーザー確認済みデータだけを保存するという原則に反する。

## 将来実装時の受け入れ条件

将来これらを実装する場合は、最低限次を満たす。

- 自動 resolved の条件を広げない
- AI 候補や曖昧検索候補は `product_candidates` の補助に留める
- `ocr_suggested` alias を自動解決に使わない
- 推定数量をユーザー確認なしで `base_quantity` として保存しない
- alias source の昇格条件をテストで固定する
- 誤候補率、未解決率、alias 衝突数、数量未補完数を運用指標で確認する
- 家庭別データを導入する場合は、先に認証・世帯管理・アクセス制御を設計する
